# [[Gemini - How does a PRD looks like]]

A **Project Requirements Document (PRD)** is the North Star for any project. It’s a comprehensive guide that defines the "what" and "why" of a product before you start building the "how."

While layouts vary by company, most professional PRDs follow a structured hierarchy to ensure clarity for stakeholders, designers, and engineers.

---

## The Standard PRD Blueprint

### 1. Executive Summary & Objective

- **Problem Statement:** What pain point are you solving?
- **Goals:** What does success look like?
- **Target Audience:** Who are we building this for?

### 2. Functional Requirements

This is the "meat" of the document. It lists the specific features the product **must** have. Usually, these are organized by priority (P0 for "must-have," P1 for "should-have").

### 3. User Stories

These help the team understand the user’s perspective.
- _Format:_ "As a [User Type], I want to [Action], so that [Benefit]."

### 4. User Flow & Design Specs

This section often links to external wireframes or Figma prototypes. It describes how a user moves from Point A to Point B.

### 5. Non-Functional Requirements

These are the technical constraints that aren't "features" but are vital for performance:
- **Security:** Data encryption standards.
- **Scalability:** How many users can the system handle?
- **Platform:** iOS, Android, Web, or all three?

### 6. Analytics & Success Metrics

How will you measure if the project worked? (e.g., "Increase sign-up conversion by 15%").

---

## Pro-Tips for a Great PRD

- **Be Concise:** If a developer has to read 50 pages of fluff, they’ll miss the important bits.
- **Avoid "How":** Don’t tell the engineers how to code it; tell them what the end result needs to be.
- **Keep it Living:** A PRD isn't carved in stone; it should be updated as the project evolves.
