# Software Project Documentation Taxonomy

## Product and Project Definition

- **Project Brief / Project Charter** — Defines the project's purpose, objectives, scope, stakeholders, constraints, assumptions, and risks.
- **Product Requirements Document (PRD)** — Defines product goals, user needs, functional and non-functional requirements, priorities, and success metrics.
- **Roadmap / Project Plan** — Defines milestones, phases, deliverables, deadlines, dependencies, and resource constraints.

## Requirements and Specifications

- **Specification (Spec)** — Defines expected behavior, functional requirements, inputs, outputs, edge cases, constraints, and acceptance criteria for a system or feature.
- **User Stories** — Express user needs and desired outcomes, usually in a concise, user-oriented format.
- **Use Cases** — Describe interactions between users or external systems and the product, including main flows, alternative flows, and failure scenarios.
- **API / Interface Contract** — Defines communication interfaces, endpoints, payloads, schemas, errors, authentication, versioning, and compatibility.
- **Data Model / Schema Specification** — Defines entities, fields, types, relationships, invariants, validation rules, database constraints, migrations, and data ownership.

## Architecture, Design, and Decisions

- **Architecture Document** — Describes system context, components, responsibilities, relationships, communication, data flows, deployment, and cross-cutting concerns.
- **Technical Design Document (TDD) / Design Doc** — Describes the proposed implementation of a feature or component, including algorithms, data structures, interfaces, processing flows, error handling, and testing considerations.
- **Architecture Decision Record (ADR)** — Records an important technical decision, its context, alternatives, rationale, consequences, and status.
- **RFC (Request for Comments) / Technical Proposal** — Presents a proposed technical change for discussion, review, and approval before implementation.
- **Engineering Standards / Technical Conventions** — Defines shared coding conventions, naming rules, error handling, logging, module boundaries, dependency rules, testing expectations, security requirements, and documentation practices.

## Execution and Project Tracking

- **Implementation Plan / Task Breakdown** — Converts a design into tasks and subtasks, defining execution order, dependencies, affected components, and completion conditions.
- **Issue / Bug Report** — Records a problem, requested change, or unit of work, including reproduction steps, expected and actual behavior, priority, status, dependencies, and acceptance criteria.
- **Meeting Notes / Progress Reports** — Capture discussions, status updates, blockers, decisions, commitments, and action items.
- **Change Log / Change Request** — Records changes, their rationale, requested scope, approvals where necessary, and release history.

## Testing and Quality Assurance

- **Test Plan** — Defines the testing strategy, scope, environments, test types, test data, quality gates, coverage expectations, and exclusions.
- **Test Cases / Acceptance Tests** — Define concrete scenarios, inputs, actions, and expected results used to verify requirements and behavior.
- **Verification Report** — Records the results of testing and other verification activities, including CI results, benchmarks, security scans, and release validation.

## Release, Deployment, and Maintenance

- **Deployment / Operations Guide** — Explains how to build, configure, deploy, and run the system, including environment setup, configuration, secrets, migrations, monitoring, rollback, and recovery.
- **Runbook / Troubleshooting Guide** — Provides operational procedures for diagnosing and resolving known failures and incidents.
- **Release Notes** — Summarize features, fixes, breaking changes, known issues, and migration steps associated with a release.
- **User Documentation** — Explains how to use the product through tutorials, guides, reference material, and troubleshooting instructions.
